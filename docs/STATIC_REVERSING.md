## 设备与传输层证据

- `config.xml` 的 USB 设备条目精确为 `VID_0C45&PID_8009&MI_00`、产品名 `USB KEYBOARD`；这与本机已验证设备一致。配置还列出 2.4G 接收器 `0C45:FDFD`，但未在本机验证。
- 控制程序导入 `SETUPAPI.dll`、`CreateFile`、`ReadFile`、`WriteFile`、`DeviceIoControl`，并动态解析 `HidD_GetFeature`、`HidD_SetFeature`、`HidP_GetCaps` 等 `hid.dll` API。
- 程序内直接构造标准 HID class GUID。`DeviceIoControl(0xB0192)` 是 `IOCTL_HID_GET_FEATURE`（`0x4520b0`），用于写入后读回设备应答，不是获取报告描述符（2026-10-16 更正）。
- `HidD_GetFeature` 的调用明确使用 `0x41`（65）字节缓冲区。这与 macOS 实测“64 字节 Feature 载荷 + 1 个报告 ID”的时钟控制通道相符。
- Output 传输封装会读取 HID caps 中的 Output 报告长度、按需补零，然后以异步 `WriteFile` 发送；它不是普通文件写入。
- 已定位到一个 33 字节逻辑 Output 包构造器：它会写入低 8 位字节和校验并重试读取确认。此处尚未把具体调用点可靠映射到某个用户功能，因此不能将它的字段或 opcode 直接复用于 macOS。

### 传输

- 唯一的 `HidD_SetFeature` 调用在 `0x452010`。长度固定 65。缓冲区第 0 字节保持 0，第 1 字节起是 64 字节载荷。
- 载荷第 0、1 字节依次是 `04` 和命令号。会话几乎总是先发 `04 18`，改完再发 `04 02`；灯效类再发 `04 F0` 结束。`04 02` 在音乐律动里每一帧都会发，所以它更像“提交/应用”，未必代表写入闪存。
- 前导包（`04 13`、`04 20`、`04 28`）的载荷偏移 8 是后面紧跟的 64 字节数据包个数：`04 13` 和 `04 28` 为 1，`04 20` 为 3 或 8。
- 单包发送 `0x44faa0(buf, len, ack)`：先 `Sleep(cmd_delaytime)`（`rgb-keyboard.xml` 中为 35 ms），再把 `buf` 的前 64 字节放到报告 ID 0 后面发出。`ack` 为 1 时再 Sleep 一次，用 `IOCTL_HID_GET_FEATURE` 读回 65 字节，读回载荷偏移 3 必须为 `0x01` 才算成功。调用方都不检查返回值，失败也会继续发后面的包。
- 时钟四个包都要求 ACK。基础灯效里 `04 18`、`04 13`、`04 02` 要求 ACK，数据帧和 `04 F0` 不要求。
- 调用方给的长度超过 65 时走分片：按 64 字节切片，每片仍包成 65 字节 Feature，不读 ACK，失败最多重试 10 次。
- 对象 `+0x784 == 2` 时走 2.4G 分支，改用 `05 10`、`07 10` 这类短包。蓝牙没有设置写入路径；语言文件写明蓝牙下不支持设置。
- 屏幕 bulk 另有 `04 72` 之后的 4096 字节拷贝，对应已发现的 4 KiB Output 通道。`0xFF13` 时钟口只走 Feature。macOS 的 IORegistry 里，`0C45:8009` 的接口 2（usage page `0xFF68`、usage `0x61`）Output 报告上限 4096、Input 64；接口 3 是 `0xFF13`，Feature 64。
- 实时灯效用另一个发送函数 `0x44fc90`：单包为 Sleep 5 ms、SetFeature、Sleep 5 ms、GetFeature，偏移 3 为 `0xFF` 时重试一次；长包每 64 字节一片、片间 Sleep 2 ms，总耗时超过 100 ms 就放弃。

### 自定义颜色 `04 23` 和 `04 F5`

两条路径用同一套记录。键位先用 `key_code` 查表，得到 `rgb-keyboard.xml` 里的 `light_index`。

`+0x7AC != 0` 时，记录从 `light_index * 4` 起，4 字节：

| 偏移 | 内容 |
|---|---|
| 0 | `light_index` 的低字节 |
| 1 | R |
| 2 | G |
| 3 | B |

`key_rgb` / `rgbvalue` 是 Windows COLORREF，内存字节就是 R、G、B。读回时 `0x42b1e0` 把它拼成 `R \| (G<<8) \| (B<<16)` 写回按键对象。

`+0x7AC == 0` 时，每个灯只占 1 字节，位置就是 `light_index`。非 0 表示这颗灯被选中；上传时写成 `0xFF`。读回时该字节做 `byte * 255 / 256`，再扩成 R=G=B 的灰色。

`04 F5` 的请求是载荷开头两字节 `04 F5`。应答按 64 字节一块抄回，最多 9 块、共 576 字节，然后按上面的记录解释。里面没有电量字段。

2026-10-16 复核（指令级）：

- `+0x7AC` 在 `0x41dcdd` 取自 `rgb-keyboard.xml` 的 `rgb_keyboard` 属性，等于 1 时为 1。本机配置为 1，所以是每灯 4 字节、9 块。
- `0x44c4e0` 发五包会话：`04 18`（ACK）、`04 13` 偏移 8 = 1（ACK）、数据帧 `80 00 00 00 00 00 00 00 00 <亮度> 00 00 00 00 AA 55`、`04 02`（ACK）、`04 F0`。亮度取页面对象 `+0x814`。
- `0x44c5f0` 接着发 `04 18`（ACK）、`04 23` 偏移 8 = 9（ACK）、576 字节分 9 片（不读 ACK）、`04 02`（ACK）、`04 F0`（ACK，这里和基础灯效不同）。缓冲先清零，只给方案里有颜色的键写 `[4·灯号] = 灯号` 和 R、G、B，偏移 574–575 写 `AA 55`。
- `0x44ff70` 读回：发 `04 F5` 偏移 8 = 9，读一次得到 ACK（失败最多重试 10 次），再固定读 9 次、每次 64 字节。`0x42b1e0` 读完总会再发 `04 02`（ACK）。
- `0x42b1e0` 只在后台线程空闲时、当前页面为 3 时被轮询调用，所以“读回 + `04 02`”在 Windows 上是例行操作。

| 2 | 普通层 `04 11`、Fn 层 `04 27`，偏移 8 = `09` | 要求 |

### 宏 `04 19` / `04 15`

`0x42db70` 的发包顺序：

| 序号 | 载荷 | ACK |
|---|---|---|
| 1 | `04 19`（没有 `04 18`） | 要求 |
| 2 | `04 15`，偏移 8 = 块数 N | 要求 |
| — | Sleep 30 ms | |
| 3 | N × 64 字节 | 不读 |
| — | Sleep 30 ms | |
| 4 | `04 02` | 要求 |

没有 `04 F0`。发送前若 `8 × (录制事件总数 + 列表项数) > 0xA8C` 就整次放弃。

缓冲 3584 字节先清零：

- 偏移 0–399 是 100 项索引，每项 4 字节。第 i 项对应列表里第 i 个宏：有事件时为数据块偏移（小端 16 位）加 `00 00`；没有事件时为 `FF FF FF FF`；未用为 0。
- 数据块从 `0x190` 开始，块头 8 字节，前两字节是本块条目数 n（小端）；后接 n 个 4 字节条目，下一块紧接其后。
- 每个录制事件写一条动作，再写一条延时：按下键 `00 00 <HID> B0`，松开键 `00 00 <HID> 30`，鼠标按下 `00 00 <键位> 90`，松开 `00 00 <键位> 10`（左 1、中 4、右 2）；延时 `<毫秒低> <毫秒高> 00 50`，不足 10 ms 按 10 ms。
- 设最后一块结束偏移为 E：E 为 64 的倍数时 N = E/64 + 1，否则 N = E/64 + 2（会多出一整块 0）。偏移 N×64−2 写 `AA 55`。

播放方式和次数不在宏缓冲里，而在触发它的改键记录里。`t_macro_data` 的 `play_times`、`delay_type`、`delay_time` 不参与上传。驱动没有看到宏数量超过 100 时的保护。

### 屏幕图像 `04 72`

界面上只有一条上传路径，也就是「开机动画」（ID 848 只是这里的提示框标题）。`0x422b00` 的发包顺序：

| 序号 | 传输 | ACK |
|---|---|---|
| 1 | Feature `04 18` | 要求 |
| 2 | Feature `04 72`，偏移 2 = 槽位，偏移 8–9 = 块数 B（小端） | 要求 |
| 3 | B 个 Output 报告，每个 `00` + 4096 字节；每写一块读一次输入报告（超时 300 ms，内容忽略） | 无 |
| 4 | Feature `04 02` | 要求 |

只发一个 `04 72`（初稿写成每块一个），没有 `04 F0`，块与块之间没有额外等待。槽位是屏幕列表当前选中项加 1；本机 `gif_count=1`，只能是 1。

总长度 T = 256 + 240 × 135 × 2 × F，F 为帧数（上限 `gif_maxframes`=141），B = ⌈T / 4096⌉。缓冲先全部填 `0xFF`：

- 头 256 字节：偏移 0 是帧数 F；偏移 1…F 是每帧延时，单位 2 ms（毫秒数除以 2，小于等于 1 时写 1，超过 510 ms 会按字节截断回绕）；其余为 `FF`。头里没有宽高、槽位或校验。
- 第 i 帧从 256 + i × 64800 开始，240×135、逐行自上而下、每行自左向右，RGB565 小端（R 高 5 位、G 中 6 位、B 低 5 位，见 `mui.dll` `0x1003c8f0`）。
- 一帧共 16 块（65536 字节，末尾 480 字节为 `FF`）；141 帧为 2231 块。

### 实时灯效

驱动的「实时灯效」页（ID 55）没有一次性下发：页面打开期间，后台线程每轮（至少间隔 30 ms）调用 `0x428110` 推送一帧，关掉页面就停。动画在 `mui.dll` 的 `CustomLightMode` 里计算，效果编号（1、4、5、7、9、10、11、12、0）只在电脑端使用，不发给键盘。音乐律动走同一帧格式。

每帧经 `0x44fc90` 发送：`04 20` 偏移 8 = `08`（要求 ACK，失败就跳过这一帧）→ 512 字节分 8 片 → `04 02`。没有 `04 18`、`04 F0`。数据按顺序逐条写 `[灯号, R, G, B]`，不按灯号定位；104 颗键用 416 字节，其余为 0，没有 `AA 55`。

### 音乐律动

`0x4339f0` 每一帧先对每个灯调用 `mui.dll` 的 `KeyboardCtrl::SetKeyColor(int, unsigned long)` 更新软件里的键盘预览。只要这一帧有灯亮，就按连接模式下发：有线（`+0x784 == 0`）调用 `0x432e70` 发 `04 20` 逐键颜色帧，2.4G（`+0x784 == 2`）调用 `0x4330b0`。键盘上的实时律动由这台程序逐帧下发（2026-10-16 更正，初稿写成“不写 HID”）。

灯字节来自前景缓冲。值 `0xFF` 表示这个槽跳过。模式值等于 100 时，第二个参数是键索引；否则是调色板 `+0x50CA0` 里的 COLORREF，下标是 `(高字节 << 8) + 低字节`。

保存下来的前景模式、振幅、背景模式、背景亮度在 `t_musiclayer_data`。应用函数 `0x433280` 只读这张表并比较本机声卡名，本身不调 `HidD_SetFeature`。

## 2026-10-16：电量（驱动与固件，只读静态分析）

驱动 `DeviceDriver.exe`（llvm-objdump 指令级，主会话完成）：

- 全程序只有 `0x435f71` 一处调用 mui.dll 的 `BatteryCtrl::SetBatteryInfo(int, int)`。所在函数 `0x435ea0` 开头判断连接模式 `+0x784 == 2`，不是就返回。`config.xml` 里模式 0 是 USB（`0C45:8009`），模式 2 是 2.4G 接收器（`0C45:FDFD`，接口 `MI_03`）。**有线模式下驱动不读电量。**
- 2.4G 下最多每 15 秒读一次（`GetTickCount` 差值不小于 `0x3A98`；参数非 0 时立即读）。请求缓冲 65 字节清零后，下标 1–2 填 `20 01`，交给 `0x4501c0`。`0x4501c0` 把各字节之和写到下标 `0x20`，用 `WriteFile` 写 33 字节，再用 `ReadFile` 读应答；应答前 3 字节须等于请求下标 1–3（`20 01 00`），不符时每 10 ms 重读，最多 20 次。符合后把 33 字节应答拷回调用者的缓冲区（`0x45033b`）。
- 调用者在应答 `[0] == 0x20` 且 `[3] != 0` 时，把 `min([3], 100)` 作为电量传给 `SetBatteryInfo`，第二个参数固定为 0。

键盘固件 GK8360 V1.17（子代理按指令追踪；主会话抽查了 `0x6B74`、`0x10B04` 和 `0x8F80` 的内容，与报告一致）：

- 电量来自 I2C 电量计，不是 ADC。读寄存器的函数在 `0x8C00`，器件地址 `0xC6` / `0xC7`。`0x148E4` 把寄存器 4–5 按 `×100 / 0x5F00` 换算成百分比，超过 100 截到 100。显示用的百分比在 `0x20000102`，0–5 的电量档位在 `0x20000101`。屏幕主页面在 `0x10B04` 读 `0x20000102` 画数字。[推断] 电量计是 Cellwise CW20xx 一类。
- 有线 USB：USB 命令处理范围（`0x1E00`–`0x2460`、`0x4A9C`–`0x5500`）内没有读取上述电量变量的代码。
  - `0x05` 读的是闪存 `0x8F80` 处的固定信息块 `40 30 00 00 AC 05 4F 02 17 01`。[推断] 其中含版本号 1.17。
  - `F6` 在应答字节 4 回一个只有初值 `0x50`、找不到写入点的变量。
  - `F0`–`F4`、`E0`、`AB` 都不回数据。
  - `04 02` 应答的字节 4–7 是本次传输的校验和，此前看到的 `84 01`、`F1 1A` 就是它。
  - 结论：**有线 USB 下键盘不提供电量。** 这是对 V1.17 的静态结论。交叉引用按文字池地址追踪，经寄存器间接写入的路径可能漏掉。
- 2.4G：键盘经 UART（`0x40054000`）和无线模块通信，收到的 `81` 帧由 `0x67C8` 按载荷首字节分发。命令 `0x20` 的处理在 `0x6B74`，把 `0x20000102` 写到应答字节 3，与驱动的解析一致。没有找到键盘主动上报电量的代码。[推断] 接收器只做转发；接收器固件未分析。
- 充电：`0x28FE` 读 GPIO1 第 17 位，消抖后写入 `0x20000065`。[推断] 这是“正在充电”标志，屏幕电池图标和灯光电量指示的颜色都按它选。USB 和 2.4G 的应答都不带这个标志。
- Feature 报告前 8 字节为 `AA 42 89 5A FF 71 62 CC` 时，固件跳到 `0x209A`。[推断] 这是进入升级模式的魔数，任何情况下都不要发送。

## 2026-10-16：macOS 实机验证

USB 模式，`0C45:8009` 的 `0xFF13` 接口。使用两个一次性 IOKit 探针，每包前等 35 ms，要求 ACK 的包写完再等 35 ms 读回 64 字节 Feature（macOS 读回不含报告 ID）。

**ACK 校准**：发送已验证的时钟四帧（UTC+8）。写入前读回全 0。三个命令包的应答都是命令字原样回显，偏移 3 为 `0x01`；数据帧的应答是整帧原样回显，偏移 3 是年份字节，不是 ACK。所以 ACK 只对 `04 xx` 命令包有意义，判定规则为“读回前两字节等于命令字，且偏移 3 为 `0x01`”。

**基础灯效**：按上文五包顺序发送模式 1（静态恒亮）、颜色 `00 FF 00`、多彩 0、亮度 5、速度 3、方向 0。三个要求 ACK 的包都通过。键盘变为全键静态绿色；拔插数据线、拨到其他档再拨回 USB 后仍是绿色，说明 `04 02` 会持久化。这次 `04 02` 的应答偏移 4–5 为 `07 02`（时钟流程里同位置为 `00 00`），含义未知。

**自定义单键颜色**：切到模式 `0x80`（亮度 5）后连读两次 `04 F5`，两次相同，104 颗键全为 0（此前没有保存过自定义颜色）。在此基础上把 Esc（灯号 1）设为 `FF 00 00`，按上文格式发 `04 23`，所有 ACK 通过；读回 Esc 为 `FC 00 00`，其余键不变。用户确认只有 Esc 亮红色，拔插或切档后仍保留。同一流程在模式 1/16 下读 `04 F5` 时，三次结果各不相同，非零区域随动画移动。`04 02` 应答偏移 4–5 先后出现 `84 01`、`F1 1A`。随后项目 CLI `ak35i keys set W=00FF00 --apply` 读取已保存颜色、合并后写入并读回核对，结果为 Esc 红、W 绿两键有颜色。

**CLI 复测**：项目 CLI `ak35i light set` 以相同字节重发静态绿色，三个 ACK 均通过。随后发送模式 16（川流不息）、颜色 `00 FF 00`、其余为驱动默认值（亮度 5、速度 3、方向 0），数据帧 `10 00 FF 00 00 00 00 00 00 05 03 00 00 00 AA 55`，ACK 均通过，用户目测效果正常。之后用户实测确认：亮度 0 为熄灭；速度 0 最慢、5 最快；方向 0 与 1 互为反向。多彩纵横的方向 2、3 未确认。

**系统配置**：CLI `ak35i system set` 和控制中心“系统设置”页都按上文四包顺序发送 `04 17`，所有 ACK 均通过。效果用一次性 IOKit 输入监听确认：它只读 `0C45:8009` 的按键事件，试验后日志即删除。

键盘背面有 Win/Mac 拨动开关。Mac 档下，Win 键位置发 `0xE2`（Option），左 Alt 位置发 `0xE3`（Command）；Win 档下两者按标注发送。三个禁用项只在 Win 档下观察到拦截效果，结果如下（偏移 2 / 3 / 4）：

| 写入 | Win 键 | Alt+Tab | Alt+F4 |
|---|---|---|---|
| 0 / 0 / 0（基准） | 发 `0xE3` | `0xE2`+`0x2B` | `0xE2`+`0x3D` |
| 0 / 1 / 1（两次） | 单按、Win+空格都没有 `0xE3` | 正常 | 只剩 `0xE2` |
| 1 / 1 / 0 | 发 `0xE3` | 只剩 `0xE2` | 只剩 `0xE2` |
| 0 / 0 / 1（CLI、GUI 各一次） | 单按和 Win+空格都照常发 `0xE3` | 未测 | 未测 |

由此可以确认：偏移 3 = 1 时拦截 Alt+F4；偏移 2 = 1 时拦截 Alt+Tab（只测了与偏移 3 同时为 1 的情况）；写回 0 后都恢复。偏移 4 与驱动标注不完全相符：只置偏移 4 时不拦截 Win 键，偏移 3、4 同时为 1 时才拦截。Windows 驱动只勾“禁用 Window 键”时发出的就是 0 / 0 / 1，所以这是固件行为，不是本项目的发包差异。原因不明。

其余观察：

- Mac 档下 0 / 0 / 1 不拦截任何键；Mac 档下的其他组合未测。
- 拔插后设置是否保留未验证：唯一一次拔插检查用的是 0 / 0 / 1，它本来就不生效。
- 休眠 1 分钟在有线 USB 下 90 秒内没有熄灭，无法据此判断偏移 6 是否生效。
- 响应时间、Fn 开关没有可观察的效果，未验证。
- 试验结束时已写回默认帧。

**改键**：CLI `ak35i keymap set` 按上文五包顺序发送，全部 ACK 通过，效果同样用只读按键记录确认（Mac 档）。

- 写入前，CapsLock 发 `0x39`。普通层写入 CapsLock = `02 00 29 00` 后，CapsLock 改发 `0x29`（Esc），A 仍发 `0x04`；拔插后仍发 `0x29`。
- Fn+F1 默认发 Consumer `0x183`（与驱动“多媒体”特殊功能相同，macOS 不响应）。Fn 层写入 F1 = `03 E2 00 00` 后，Fn+F1 改发 Consumer `0xE2`，系统出现静音图标；单按 F1 仍发 `0x3A`。
- 两层各写一次全默认（只有 `AA 55`）后，CapsLock 回到 `0x39`，Fn+F1 回到 `0x183`。由此确认全 0 记录就是固件默认，Fn 层写全 0 不会清掉出厂 Fn 功能（只验证了 F1）。

macOS 会忽略很短的 CapsLock 点按（实测按住约 0.55 秒后大写状态才翻转），所以不能用大写灯判断 CapsLock 是否改键成功，以按键记录为准。

**宏**：CLI `ak35i macro set "A" "Shift+B"` 按上文顺序发送（两个宏，E = 464，9 块），再用 `ak35i keymap set F12=macro:1 F11=macro:2:x3` 绑定，全部 ACK 通过。这把键盘的 F 行默认是媒体键：F12 发 Consumer `0xE9`（音量加），F11 发 `0xEA`（音量减）。

- 绑定后 F12 播放 A 按下、20 ms、A 松开。
- F11 播放 Shift 按下、B 按下、B 松开、Shift 松开，每步间隔 20 ms，重复 3 次。两次重复之间约 10 ms，没有等满最后一步设置的 20 ms。
- 拔插后两者仍然播放。
- 上传空宏表（8 块全 0，偏移 510–511 为 `AA 55`）、两层改键写回默认后，F12/F11 回到音量加减。

由此确认索引表、块头、按下/松开标签、延时条目、`06 序号 方式 次数` 记录（序号从 0 开始）以及块数公式。鼠标事件、方式 2/3、清空后是否真的删除了宏（没有绑定去试）尚无实机证据。代理报告在 §2.5 示例里把 E 算成 0x1B0，按规则应为 0x1A8，两者得出的块数相同。

**实时帧**：驱动后台线程空闲时按当前页面分支（`0x434d2f`–`0x434d99`）：第 3 页轮询 `04 F5`，第 6 页调用 `0x428110`，第 7 页在开关打开时调用 `0x4339f0`，前后包着 `timeBeginPeriod(1)` / `timeEndPeriod(1)`，推流前后都不切换灯效模式。发送函数 `0x44fc90`：命令包前后各等 5 ms，读回偏移 3 为 `0xFF` 时立即重写一次再读，偏移 3 为 `0x01` 算成功；分片间隔 2 ms，超过 100 ms 放弃。

CLI `ak35i live` 按此时序推送（每帧至少间隔 33 ms，macOS 上实际约 67 ms 一帧）。全键蓝色推送 15 秒：键盘全程显示蓝色，219 帧全部确认；停止后立即恢复原灯效。彩虹波浪、呼吸、繁星和音乐律动（Core Audio 系统音频 + 16 段 FFT）用户目测正常。由此确认 `04 20` 帧只覆盖显示、不改变保存的灯效，记录按顺序排列即可（每条带灯号）。

**屏幕**：CLI `ak35i screen set --test-pattern --apply` 按上文顺序上传单帧测试图（16 块）：`04 18`、`04 72`（`01` 槽位，块数 `10 00`）在 `0xFF13` 接口确认；每块 4096 字节 Output 报告写到 `0xFF68` 接口后，键盘都回一个 Input 报告 `01 5A 02 00…`，与固件 `0x4C6A` 处设置的回复一致，每块约 0.16 s；`04 02` 确认。屏幕随即显示测试图，方向（左上白块、右下黑块）和颜色顺序正确。拔插后上电仍播放出厂开机动画，与固件分析的 `0x340000` / `0x950000` 分区一致；动画播完后回到原来的界面，测试图不再出现。

固件 V1.17 的按键表（`0x15ADC` 起，按列排列，每列 8 行）之后是两张 Fn 组合表（`0x15B84` 起，按键码与动作码成对）。其中 Fn+Q/W/E/R/T 产生动作码 `0xEA`/`0xEB`/`0xEC`/`0xFB`/`0xFC`，分别把屏幕显示模式设为 1/2/4/8/`0x10`（`0x2F90`–`0x30C8`，都要求另外两个状态字节满足条件）；播放器在开机动画结束、模式为 8 时加载 `0x950000`（`0x123CC`）。切换到模式 `0xC` 的动作码 `0x9D`（`0x3104`）不在这两张表里，来源未找到。用户实测按 Fn+R 屏幕没有变化，原因不明（前提条件不满足，或键盘固件与 V1.17 不同）。说明书（Manuals+ 收录的 AK35I V3 MAX 用户手册，未能直接打开原文，取自搜索摘录）写明 Fn+PrtSc 打开动画、再按返回主页面；用户拔插后按 Fn+PrtSc，屏幕显示上传的测试图，再按返回。由此确认 GIF 页内容断电后保留，Fn+PrtSc 对应切换模式 `0xC` 的动作，但它在固件里的来源表没有找到。多帧动画和帧延时尚未实机验证。

## 当前边界

静态逆向已经把控制程序的功能面和每条写入的命令字分开。时钟四帧、基础灯效 `04 13` 和自定义单键颜色 `04 23` / `04 F5`（驱动里的「用户灯光」）已有 macOS 实机证据（报文、ACK、效果、重连后仍在；灯效目测确认了模式 1 和 16）。系统配置 `04 17` 的禁用 Alt+Tab / Alt+F4 已有实机证据，禁用 Win 只在与禁用 Alt+F4 同时开启时生效；休眠、响应时间、Fn 开关和持久化尚无证据。改键 `04 11` / `04 27` 已有实机证据（普通键和媒体键，两层，持久化，恢复默认）。宏 `04 19` / `04 15` 已有实机证据（按键事件、单次和重复播放、持久化；清空只确认了 ACK）。实时帧 `04 20` 已有实机证据（显示、停止后恢复）。屏幕 `04 72` 已有单帧上传的实机证据，并确认不影响出厂开机动画。

## 后续

每个功能进入 macOS 协议层前，都要有“报文 → 设备 ACK → 实际效果 → 重连后仍在”的证据。证据可以来自 macOS 实机试验（基础灯效即如此），也可以在 Windows 上按 [抓包工作单](CAPTURE_WORKSHEET.md) 抓包。

改键、宏、屏幕都无法读回，试验前要先有恢复手段：

- 改键：驱动「重置键盘」发的就是两层全 `00 00 00 00`（偏移 574–575 为 `AA 55`），可作为恢复镜像。
- 宏：没有宏时驱动发 8 块全 0（偏移 510–511 为 `AA 55`）。
- 屏幕：安装包里只有 `gif/AJAZZ AK820Pro/0.gif`（128×128，属于另一型号），没有本机出厂开机动画。覆盖后原动画无法恢复。
- 系统配置：默认帧 `00 01 00 00 00 00 02 00 02 00 … AA 55` 可作为恢复镜像；但键盘当前值读不出来，若用户改过设置，恢复默认会丢掉原值。
